# 使用说明与来源职责

## 1. 这套知识库解决什么问题

本知识库用于生成、审查和修订逐点 reviewer response。它的唯一风格基准是江 TIE_2621 范例中经验证的场景组织、功能块推进和句子实现：如何进入实质，如何按 reviewer situation 安排实验、推导、比较与图表，以及如何让证据和修改位置可核查。结论是否需要出现及其证据范围由独立质量审计判断。

它不是一般 academic-writing 手册，不是固定 phrasebook，也不保存某一篇论文的变量、数值、图号或 citation 编号。未来 Agent 必须先以新 comment 和新项目 primary evidence 确定事实、可支持的 claim 与真实修改状态，并识别作者明确确认的 scientific mainline、concern decomposition 和主要回应顺序；这些明确指定的内容构成当前项目的 response constraints。在这些约束下，本库用 TIE-native 机制决定尚有自由度的组织与表达，并完成独立质量审计。

## 2. 三层知识结构

本库共有 **15 个最终知识单元**。

### 2.1 TIE-native core：7 个主体单元

| ID | 单元 | 主要职责 | 主文件 |
|---|---|---|---|
| TN-01 | 首段实质落地 | 感谢后尽快给直接答案、已做动作或新增证据 | `01`、`02` |
| TN-02 | concern 驱动的回复主干 | 让每段只推进当前 concern 的一个判断 | `01` |
| TN-03 | evidence block | 将服务同一子问题的实验或推导组成连续证据单元 | `01`、`03` |
| TN-04 | 图、caption 与正文协作 | 让图可识别、正文可判断、引用可定位 | `03` |
| TN-05 | 结果读取 | 明确读出 concern-relevant 现象，包括实质不利结果 | `03` |
| TN-06 | 句子功能与节奏 | 决定下一句承担回答、目的、设置、结果、推论或定位中的哪一项 | `02` |
| TN-08 | 规模随任务复杂度变化 | 局部问题通常短，独立技术或证据任务增多时通常出现更多功能块和篇幅 | `01` |

这些单元承载经场景验证的 response 组织与实现；具体路径须由 reviewer situation 触发。其依据是 TIE PDF 的实际条目和版面，而不是总结文件中的二次抽象。

### 2.2 supporting discipline：5 个辅助单元

| ID | 单元 | 只负责什么 | 不得做什么 | 主文件 |
|---|---|---|---|---|
| SD-01 | concern—evidence—claim 对齐 | 检查证据是否直接回答判断标准、结论是否越界 | 不改写 TIE 的段落节奏 | `04` |
| SD-02 | source、provenance 与 citation | 限定来源职责、建立可追踪性 | 不从外部规则生成 TIE phrase | `04` |
| SD-03 | 术语、符号与交叉引用一致性 | 保证定义、对象、图号和版本同步 | 不替当前稿件命名 | `04` |
| SD-04 | surgical audit 与完成门槛 | 同类问题回查、状态分离、通过后停止泛化改写 | 不把局部缺陷升级为无边界重写 | `06` |
| TN-07（历史 ID） | 条件型结论与 claim gate 接口 | 新 response 确需结论时，配合 SD-01 检查证据范围与重复 | 不要求每个 block 有结论，也不把充分覆盖后停止写成 TIE 指纹 | `01`、`04` |

Nature / Academic Research Suite 只在这一层提供正确性、证据、claim、source、consistency 和 QA 纪律。它们不能覆盖 TIE 的组织与表达基准。

### 2.3 conditional supplements：3 个条件单元

| ID | 触发情形 | 单元 | 主文件 |
|---|---|---|---|
| CS-01 | 一个 comment 含多个独立 response obligations | 原子义务 inventory 与 no-silent-drop；不把支撑论据机械拆成新 concern | `07` |
| CS-02 | reviewer 漏读或误解稿件中已经存在的信息 | 将漏读视为清晰度/可见性信号 | `07` |
| CS-03 | 多位 reviewer 的报告或回复互相不可见 | reviewer 隔离与独立完整回应 | `07` |

没有触发条件时，不加载这些单元；不得把它们写进每条 response 的固定结构。

## 3. 来源层级与职责

1. **当前项目 primary evidence** 确定真实 concern、事实、可支持的 claim 与修改状态：reviewer 原 comment 界定所问问题；稿件、实验记录、正式结果图、可靠分析输出和作者确认的修改核定科学内容及动作状态。
2. **作者明确确认的 project-specific response plan** 若规定 scientific mainline、concern decomposition、主要先后关系或必要推理依赖，这些规定是当前项目的 response constraints；只列出待回答事项而未规定顺序，不冻结该顺序。作者方案不能覆盖 reviewer 的真实 concern、primary evidence 或正确性检查。
3. **TIE PDF 原文** 是唯一的 response organization / expression 风格金标准；在上述项目约束下决定功能块、信息推进、句子实现、图文关系和 same-author 节奏。未由作者明确规定的组织自由度，仍由 TIE-native 机制决定。
4. **阶段 1/2 裁决** 决定已验证的可迁移机制、真实错误、适用边界和不得重开的未决项。
5. **Nature / Academic Research Suite** 只补足覆盖、证据、claim、source、consistency 和 reviewer 隔离纪律，不代替作者方案或 TIE 组织。
6. **三份 TIE 总结** 只用于定位和解释。若其概括、补写样句或“项目增强”与 PDF 不同，以 PDF 为准。

来源不得越权：范例不能替新稿件定义变量，也不能仅凭一般组织倾向重排作者明确确认的主要科学回应顺序；作者方案不能使缺失的证据成立；稿件不能证明 TIE 惯用句式；脚本或代码图注不能替正式结果；派生总结不能冒充 primary source；多个重复总结不增加独立证据强度。若作者方案与 reviewer concern、primary evidence、可支持的 claim 范围、数学或前后逻辑明确冲突，Agent 须指出具体冲突并等待作者决定，不静默修改方案，也不机械照写。

当前组织与表达调用入口为 `04_TIE句子级表达重建/00_TIE_2621_sentence_realization基准.md`：TIE PDF 仍是原始表达金标准；该基准用 scene corpus、候选机制和 validation 限定 A1–A6（跨场景）、B1–B6（情形触发）与 C1–C6（单例参考）。面对新 comment，先判断 reviewer situation、独立 concern 和作者明确确认的项目约束，再在允许的空间内由 A/B 选择功能块及句间推进；只匹配 C 的情形需回查原 scene，不从 C 生成固定路径。最后由 `04`、`06` 执行独立质量 gate。该入口只决定现行证据等级和调用顺序，不替当前项目 primary evidence 决定事实，也不覆盖作者明确确认且无冲突的科学路线。

## 4. 推荐使用顺序

1. 先读通原 comment 的完整论证，区分支撑质疑的论据、由此形成的判断与真正的 response obligations；再结合当前项目 primary evidence 建立 concern、判断标准、所需动作和证据状态。识别作者是否明确确认 scientific mainline、concern decomposition 或主要先后关系，只将明确部分记为项目约束。若存在事实、覆盖或逻辑冲突，按 §3 报告并等待作者决定；无冲突后再按上述 realization 基准判定 reviewer situation 与 A/B/C 等级。
2. 在已确认的项目约束内，用 `01_TIE_Response_核心逻辑与组织.md` 决定尚未被指定的回复主干、功能块和 evidence blocks。
3. 用 `03_实验_结果图_Caption.md` 安排实验、图、caption 和读图句。
4. 用 `02_TIE_表达_句法_语气.md` 决定每一句的功能、承接、符号可读性和节奏；在句子与关键短语上同时调用 `04`，核对对象、条件与证据范围。
5. 用 `04_证据_Claim_术语_引用.md` 做 concern 完整度、事实、claim、数学正确性、来源和一致性检查；这些检查不能只留在整条回复的末轮，须在逐句逐词验收中落实到实际修饰关系。
6. 仅在触发条件满足时读取 `07_条件型补充规则.md`。
7. 按 `06_Response生成与验收流程.md` 分别完成 TIE-style 与 supporting audit，并用 `05_错误模式与负例.md` 阻止历史错误回流。

## 5. 泛化边界

- 迁移功能，不复制 TIE 的单句、拼写错误、非地道搭配、绝对化比较、平台、参数或图号。
- `Thanks for...`、`According to your suggestion`、`For your convenience`、`To further...` 等只证明一种可能的功能载体，不是强制模板。
- TIE 原文对某些问题回答不完整，尤其 R4-4；这些位置用于建立负例，不因来自 benchmark 而被洗白。
- 当前 Comment 1 中的评价指标、公式、任务数、设置、数值、figure、citation 编号和 reviewer 扫读假设均是项目材料，不进入通则。
- 已在阶段 1/2 排除、降级、替代或保留未决的内容，不在本库重新裁决。

## 6. Provenance 记法

- `TIE Rn-m, PDF p.x`：TIE PDF 的具体 reviewer 条目与物理页。
- `CK-xxx`：阶段 2 审核后的候选。
- `ESC-xxx`：阶段 2 条件型外部补充候选。
- `CI-xxx / EV-xx`：阶段 1 的裁决或演变链，主要用于负例和边界。
- `supporting`：Nature / Academic Research Suite 只作为兼容性、事实性或 QA 辅助，不作为 TIE 文风证据。

## 7. 独立使用要求

只依赖本知识库时，Agent 仍须取得新项目的原始 comment 与可检查材料。若关键事实、实验状态、修改位置或 citation 不可验证，必须显式标记缺口；不得用 TIE 风格写出“像完成了”的句子来替代真实完成。
